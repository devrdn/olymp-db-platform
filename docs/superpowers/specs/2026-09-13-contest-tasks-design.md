# Несколько задач в одной олимпиаде

Дата: 2026-09-13. Статус: **отложено**. Решения ниже согласованы, реализация не
запланирована: пока олимпиаде достаточно одной задачи. Документ существует,
чтобы при возвращении к теме не обсуждать всё заново и чтобы работа, которая
идёт раньше (лидерборд), не закрыла эту дорогу.

## Задача

Сегодня олимпиада — это одно дело: одна история, одна игровая база, один список
вопросов. Нужна олимпиада как список задач, где у каждой задачи своё содержание,
а время, участники и зачёт общие.

## Принятые решения

1. **У каждой задачи своя игровая база.** Свой шаблон — дамп, конструктор таблиц
   или скрипт. Копия для участника создаётся, когда он впервые открывает задачу.
2. **Все задачи открыты сразу.** Участник сам выбирает, с чего начать. Порядок в
   списке — только порядок показа.
3. **Настройки вопросов у каждой задачи:** один или несколько вопросов, свободное
   или последовательное прохождение. Последовательность действует внутри задачи.
   Штраф и так задаётся на вопросе.
4. **Победитель в режиме `winner`** — тот, кто раньше всех верно ответил на
   финальные вопросы всех задач; момент победы — время последнего из этих
   ответов. С одной задачей это ровно сегодняшнее правило.
5. **Своего лимита времени у задачи нет.** Время задаёт олимпиада — общим окном
   или индивидуальным таймером, — и дедлайн участника остаётся одной формулой
   (раздел 8).

## Модель

Олимпиада становится контейнером; задача — это то, чем олимпиада является по
содержанию сегодня.

| Олимпиада | Задача |
|---|---|
| название, описание, языки | название (по языкам), порядок |
| окно, таймер, запись, IP-ограничения | история |
| участники, менеджеры | игровая база: шаблон, загрузка дампа, данные конструктора |
| режим оценки, лидерборд, заморозка | режим вопросов, прохождение |
| | вопросы и эталонные ответы |
| | политика SQL |

**Совместимость.** Миграция превращает каждую существующую олимпиаду в олимпиаду
с одной задачей. С одной задачей экран игры и админка выглядят как сегодня:
переключатель задач не показывается.

## Схема

- `tasks (id, contest_id, ord, question_mode, progression, created_at,
  updated_at)`, `UNIQUE (contest_id, ord) DEFERRABLE` — как у вопросов;
  `task_translations (task_id, lang, title)`.
- `contests.question_mode` и `contests.progression` переезжают в `tasks`.
- `task_id` вместо `contest_id` у: `stories` (`UNIQUE (task_id)`),
  `game_templates` (`UNIQUE (task_id)`), `game_uploads`, `game_table_data`,
  `contest_sql_policies` (переименовать в `task_sql_policies`, ключ `task_id`),
  `questions` (`UNIQUE (task_id, ord)`).
- `game_instances`: добавляется `task_id`; уникальность — `(registration_id,
  task_id)` вместо `registration_id`. Внешний ключ проверяет, что регистрация и
  задача принадлежат одной олимпиаде (составной ключ, как сегодня у
  `registrations (id, contest_id)`).
- `query_log.task_id` — журнал должен говорить, в какой базе выполнен запрос.
- `contest_id` там, где он остаётся нужен для индексов и прав (`game_instances`,
  очистка по статусу олимпиады), сохраняется рядом с `task_id`, согласованность
  держит составной внешний ключ.

Миграция одна, в транзакции: создать по задаче на олимпиаду, перенести ключи,
затем снять старые ограничения. На момент решения в базе только тестовые
олимпиады, но миграция пишется так, будто данные настоящие.

## Бэкенд

- **Провижининг** (`internal/provisioning`): `Ensure(contest, task,
  registration)`; пул заготовок и его размер — на задачу; квота диска считается
  по сумме шаблонов задач; очистка идёт по статусу олимпиады, как сейчас, но
  шаблон освобождается, когда ушли все копии **этой задачи**.
- **Прокси запросов** (`internal/queryproxy`): доступ проверяется к олимпиаде,
  база выбирается по задаче; политика SQL — задачи.
- **Ответы** (`internal/contests`): последовательность и режим одного вопроса
  проверяются в пределах задачи; гейт публикации проверяет каждую задачу
  (история на всех языках, вопросы, эталоны, игра собрана) и олимпиаду (есть хотя
  бы одна задача; в `winner` у **каждой** задачи есть финальный вопрос).
- **Query Runner не меняется:** он получает имя базы.
- **Пакет олимпиады** (экспорт, будущий импорт): версия формата 2 — список задач;
  версия 1 читается как олимпиада с одной задачей.

## API

Маршруты содержания получают задачу:
`/contests/{id}/tasks/{taskId}/story`, `…/game…`, `…/questions…`,
`…/sql-policy`; участника — `/contests/{id}/tasks/{taskId}/play/story`,
`…/play/questions`, `…/play/schema`, `…/query`. Добавляются
`GET/POST /contests/{id}/tasks`, `PUT/DELETE /contests/{id}/tasks/{taskId}`,
перестановка задач. Журнал участника (`/play/log`) остаётся на олимпиаде и
получает фильтр по задаче. Около 30 маршрутов, изменение в основном механическое.

Задачу нельзя добавить или удалить, когда олимпиада `running` и позже — по той
же причине, по которой сейчас нельзя менять содержание (`ContentEditable`).

## Интерфейс

- **Админка:** в олимпиаде список задач (добавить, переименовать, переставить,
  удалить); у каждой задачи свои разделы «История», «Игра», «Вопросы», «Базы
  данных», «Политика SQL». Настройки времени, участников и зачёта остаются на
  олимпиаде.
- **Экран игры:** переключатель задач над панелями; консоль, схема, история и
  вопросы — выбранной задачи; запрос и размеры панелей запоминаются на задачу.
  Таймер один.
- **Раздел «Базы данных»** группирует копии по задачам.

## Цена

**Диск — главная цена, и он растёт с числом задач.** 40 участников × 3 задачи по
600 МБ — 72 ГБ копий, если создавать всё сразу. Смягчают: копия создаётся при
первом открытии задачи (кто не дошёл до задачи, тот не занимает под неё место);
пул заготовок на задачу меньше; маленькие базы (7–50 МБ) почти ничего не стоят.
Проверку места до создания копии (`game_cluster_full`) это не отменяет.

**Объём:** около 10–15 Go-файлов (провижининг, прокси, ответы, гейт, экспорт,
очистка), около 30 маршрутов, около 30 файлов фронта, одна миграция с переносом
данных. Самые рискованные части — миграция и провижининг.

## Как это касается лидерборда

Лидерборд делается раньше и для одной задачи, но так, чтобы задачи потом
легли без переделки:

- ранжирующий запрос считает по регистрации через `submissions → questions`, и
  добавление `questions.task_id` его не ломает;
- ответ API держит строку открытой для расширения: колонки по задачам появятся
  отдельным полем (`tasks: [{points, solved}]`), а не заменой существующих;
- правило победителя в режиме `winner` из этого документа (п. 4) с одной задачей
  совпадает с правилом лидерборда, поэтому гейт `winner_needs_final` при переходе
  на задачи только расширяется до «в каждой задаче».
