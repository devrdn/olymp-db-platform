# Сборка игры по требованию: данные конструктора должны доезжать до базы

Данные, которые организатор вводит в конструкторе таблиц, не попадают ни в
одну базу. Не потому, что теряются — они сохраняются на волюм и в
`game_table_data` исправно, — а потому, что сборка шаблона происходит раньше,
чем появляется первая строка, и второй сборки уже никогда не будет.

## 1. Что именно сломано

Порядок, в котором это происходит на работающей установке:

1. Организатор сохраняет схему — `PUT /contests/{id}/game/definition`.
   `upsertGame` ставит `game_templates.status = 'pending'` и поднимает версию.
2. Фоновая задача `game-build` (`internal/app/background.go`) забирает **любой**
   `pending` шаблон и собирает его в течение секунд. Таблицы создаются
   пустыми: `finishDefinitionBuild` грузит данные через `Games.loadTableData`,
   а готовых CSV на этот момент ещё нет.
3. Только теперь организатор может вводить строки: `AppendTableRow` отказывает
   таблице, которой нет в **сохранённой** схеме, — то есть порядок «сначала
   данные, потом сохранение» невозможен в принципе.
4. Ни `AppendTableRow`, ни `CompleteTableUpload`, ни `DeleteTableRow` не
   трогают строку шаблона. Эндпоинта, который просит собрать заново, в
   роутере нет. Шаблон остаётся `ready`, и копии участников делаются с
   пустой базы.

Почему это пережило тесты: единственный тест, доводящий данные конструктора до
настоящего кластера, вызывает `games.Build` **после** того, как залил все
строки. В деплое `Build` вызывает планировщик, и вызывает он его сразу после
сохранения схемы. Тест проверял порядок, которого не бывает, — ровно то, о чём
правило 10 в CLAUDE.md.

Обходной путь, который работает сегодня: ввести данные и сохранить схему
второй раз, ничего в ней не меняя. Данные при этом переживают сохранение (они
удаляются только при смене источника игры), версия поднимается, сборка
забирает строки. Спека существует затем, чтобы этот фокус не был единственным
способом.

## 2. Решения

- **Игра помнит, что её данные изменились после сборки.** Не новый статус:
  шаблон, собранный до правки, по-прежнему `ready` и по-прежнему годен —
  участники просто получают прежние данные. Это признак поверх статуса, а не
  вместо него.
- **Пересборку просит человек, а не каждая строка.** Пятьдесят введённых
  строк — это пятьдесят `CREATE DATABASE`, пятьдесят поднятых версий и экран,
  который всё время «строится». Организатор вводит данные и один раз
  нажимает «Собрать».
- **Первая сборка остаётся автоматической.** Сохранение схемы собирает игру
  сразу, как сегодня; она собирается пустой, и дальше работает кнопка.
  Альтернатива — не собирать builder-игру, пока не нажмут, — экономит одну
  дешёвую сборку пустых таблиц и заводит новое состояние «схема сохранена,
  базы нет», которое пришлось бы объяснять на экране и обрабатывать всюду,
  где сегодня достаточно `ErrNoGame`.
- **Пересборка запрещена в идущей олимпиаде.** Тот же `GameEditable`, что и
  сегодня: поднятая версия делает копии участников устаревшими, а устаревшая
  копия пересоздаётся — то есть каждый участник теряет свою базу. Правка
  данных во время олимпиады — отдельная задача с другим механизмом
  (синхронизация живых копий), и эта спека её не касается.
- **Версия поднимается.** Копия несёт версию шаблона, из которого сделана, и
  только её рост делает копии устаревшими. Пересборка без поднятия версии
  собрала бы новый шаблон, которым никто не воспользуется.

## 3. Модель

`game_templates` получает колонку `data_changed_at timestamptz` (миграция 39):
момент последнего изменения данных таблиц, `NULL` — «с последней сборки данные
не трогали».

Ставят её в `now()` три операции, и только они:

- `AppendTableRow` — строка из формы;
- `CompleteTableUpload` — завершённая загрузка CSV для таблицы (в том числе
  вытесняющая прежний готовый файл);
- `DeleteTableRow` — надгробие над строкой.

Запись идёт в той же транзакции, что и сама правка и её запись в аудит: правка,
которая откатилась, не должна оставлять за собой просьбу собрать заново, а
правка, которая состоялась, не должна её терять.

`AbortTableUpload` и `BeginTableUpload` признак не ставят: незавершённая
загрузка не меняет ни одной строки, которую сборка увидела бы.

В домене:

```go
// DataChangedAt is when this game's table data last changed, or nil when
// nothing has changed since the build.
DataChangedAt *time.Time

// NeedsBuild reports a game whose built database no longer matches the data
// an organiser has since put into it.
func (t Template) NeedsBuild() bool {
    return t.Status == TemplateReady && t.DataChangedAt != nil
}
```

### Как признак снимается

`ClaimBuild` уже пишет `updated_at = now()` и возвращает строку — это и есть
момент, когда сборка увидела данные. `FinishBuild` получает его ещё одним
аргументом и обнуляет `data_changed_at` только если тот не сдвинулся позже:

```sql
data_changed_at = CASE WHEN data_changed_at <= $4 THEN NULL ELSE data_changed_at END
```

Что это даёт:

- строка, добавленная **во время** сборки, признак сохраняет, и следующая
  сборка её заберёт. Без этой проверки правка, пришедшая в середине сборки,
  исчезала бы бесследно — ровно тот класс ошибки, который эта спека чинит;
- провалившаяся сборка признак тоже оставляет: данные так и не доехали;
- сохранение схемы признак не снимает и снимать не должно — поставленная им
  `pending` сборка заберёт данные, и обнулит признак уже `FinishBuild`.

## 4. Просьба собрать

`POST /contests/{id}/game/build`, за `contest.edit` — той же дверью, что
`PUT /game/script` и `PUT /game/definition`: пересборка не опаснее замены игры,
а замена игры уже стоит за этим правом.

`Games.RequestBuild(ctx, actorID, contestID)`:

1. `GameEditable` — иначе `ErrGameNotEditable`;
2. игры нет — `ErrNoGame`;
3. шаблон уже `pending` или `building` — `ErrBuildInProgress`;
4. иначе один `UPDATE`: `status = 'pending'`, `version = version + 1`,
   `build_error = NULL`, `schema_json = NULL`, `schema_version = NULL`,
   `updated_at = now()`. Содержимое игры — скрипт, definition, upload_id — не
   трогается: это просьба собрать то, что уже сохранено, а не сохранение.
   Кэш схемы обнуляется по той же причине, по которой его обнуляет
   `upsertGame`: он описывает предыдущую сборку, и обе колонки связаны
   ограничением миграции 22;
5. запись в аудит: `contest.game_build_requested`, payload — новая версия.

Новых sentinel'ов заводить не нужно — все три объявлены. Но `ErrBuildInProgress`
объявлен и не возвращается сейчас ниоткуда: он был написан под ровно эту
кнопку и остался неподключённым. Значит он впервые доходит до HTTP, и по
правилу 1 ему нужны код `build_in_progress` в `docs/api/error-codes.json`,
строка в `en`/`ru`/`ro`, ветка в `fail` хендлера и тест, утверждающий 409.
`game_not_editable` и `no_game_yet` уже есть — им нужна только ветка на новом
маршруте и тест.

Шаг 3 и шаг 4 — не атомарная пара в Go: `UPDATE` несёт условие
`status IN ('ready', 'failed')` сам, и две нажатые одновременно кнопки дают
одну сборку, а второму нажавшему — `ErrBuildInProgress`. Проверять статус
заранее всё равно нужно, чтобы отличить «уже строится» от «игры нет».

## 5. Экран

Вкладка «Игра», под конструктором таблиц: строка состояния и кнопка.

- Данные менялись после сборки — «Данные изменились после последней сборки»
  и кнопка «Собрать заново».
- Сборка идёт — кнопка недоступна, состояние показывает уже существующий
  поллинг (`game-poll.ts`), ничего нового.
- Олимпиада идёт — ни строки, ни кнопки: пересборка запрещена, и предлагать
  дверь, за которой отказ, — это принцип 4 дизайн-спеки наоборот.

Текст — в словарях всех трёх локалей, как всё видимое.

## 6. Проверка

- **Красный тест уже написан** (`tabledata_test.go`): строка, добавленная
  после сборки, оставляет шаблон «требующим сборки». Сейчас он падает; после
  правки — проходит. Переедет с `Building()` на `NeedsBuild()`.
- Признак ставят все три операции и не ставят `Begin`/`Abort`.
- Признак снимается успешной сборкой.
- Признак **не** снимается, если строка пришла во время сборки (на фейковом
  сторе — там, где момент захвата можно задать).
- `RequestBuild`: отказ в идущей олимпиаде, отказ при идущей сборке, отказ без
  игры, успех поднимает версию и ставит `pending`.
- Хендлер: 4xx с нужным кодом на каждый из трёх отказов.
- Фронтенд (vitest): строка и кнопка появляются только при `needs_build`,
  прячутся в идущей олимпиаде, кнопка недоступна во время сборки.
- **Порядок интеграционного теста исправляется**:
  `TestAScriptSavedInTheCoreDatabaseFromATableBuilderDefinitionWithCSVDataBuildsRowsOnTheGameCluster`
  собирает сразу после сохранения схемы, затем заливает данные, затем просит
  пересборку и собирает второй раз — и только после этого считает строки.
  Иначе тот же баг спрячется снова за порядком, которого в деплое нет.
- Браузером: обе локали, обе темы, состояния «данные изменились», «строится»,
  «олимпиада идёт».

## 7. Границы

- Редактирование значения в существующей строке. Сегодня опечатка чинится
  удалением строки и вводом заново; настоящее редактирование — часть
  следующей задачи, потому что append-only файл с надгробиями меняется под
  него нетривиально.
- Синхронизация правок с живыми копиями участников и роль, которой это
  разрешено. Следующая задача целиком.
- Источники «скрипт» и «дамп». Они полны в момент сохранения, и признак
  устаревания им нечем ставить.
