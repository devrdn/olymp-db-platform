# Наблюдение за участником

Организатор олимпиады видит всё, что делал каждый участник, — вживую во время
олимпиады и полностью после неё, с фильтрами. Сейчас из всего, что
записывается, организатору не показано ничего, кроме итоговой таблицы.

## 1. Решения

- **Кто видит:** владелец и менеджеры олимпиады, плюс администраторы установки
  (`contest.admin_all`). Новое право `contest.monitor` выдаётся тем же ролям, что
  и `contest.view`. Каждый просмотр записывается в аудит (раздел 7).
- **Что видит:**
  - SQL-запросы — полностью, отдельной вкладкой;
  - попытки ответа — вместе с запросами, которые к ним привели;
  - входы и выходы с IP и браузером;
  - смена IP и одновременные сессии;
  - уход со страницы;
  - вставка текста;
  - заметки и вкладки SQL с историей правок;
  - события жизни вкладок;
  - старт часов, окончание, дисквалификация.
- **Заметки и вкладки больше не личные.** Прежнее решение (спека рабочего
  места, раздел 1: «преподаватели их не видят») отменено: организатор видит их
  и их историю. Участнику это честно сказано на экране олимпиады: строка под
  заголовком и текст в заметках (раздел 8).
- **Как:** вживую во время олимпиады (лента, которая обновляется сама, и
  таблица участников с отметками) и после (полная лента по каждому, фильтры,
  CSV).
- **Сигналы браузера — не доказательство.** Уход со страницы и вставку
  сообщает браузер участника, и он может соврать или промолчать. Экран так и
  называет их — «сигналы», — и ничего не решает за организатора
  автоматически.

## 2. Что записывается нового

### 2.1. События участника — таблица `participant_events`

Только добавление, никаких правок:

```sql
CREATE TABLE participant_events (
    id              bigserial PRIMARY KEY,
    contest_id      uuid NOT NULL REFERENCES contests ON DELETE CASCADE,
    registration_id uuid NOT NULL REFERENCES registrations ON DELETE CASCADE,
    kind            text NOT NULL,
    payload         jsonb NOT NULL DEFAULT '{}',
    client_at       timestamptz,          -- время, которое назвал браузер; только для сигналов
    created_at      timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX participant_events_registration_idx ON participant_events (registration_id, id);
CREATE INDEX participant_events_contest_idx      ON participant_events (contest_id, id);
```

`contest_id` денормализован намеренно: живая лента всей олимпиады читает
`WHERE contest_id = $1 AND id > $cursor` по индексу, без соединения с
`registrations`.

Виды событий и их поля (`payload`, каждое поле ограничено):

| `kind` | Откуда | `payload` |
|---|---|---|
| `page_left` | браузер | `{ "away_ms": int }` — сколько участника не было на странице (вкладка скрыта или окно потеряло фокус), от 1 с до 24 ч; событие приходит, когда он вернулся |
| `paste` | браузер | `{ "target": "editor"\|"answer"\|"notes", "chars": int, "text": string ≤ 500 символов }` — куда вставил, сколько символов, начало вставленного |
| `ip_changed` | сервер | `{ "from": inet, "to": inet }` — запрос участника пришёл с другого адреса, чем прошлый |
| `parallel_session` | сервер | `{ "other_ip": inet, "user_agent": string ≤ 200 }` — к той же регистрации обращается вторая сессия, пока первая жива |
| `tab_created` / `tab_renamed` / `tab_deleted` | сервер | `{ "tab_id", "title" }` (`tab_renamed` — `from`, `to`) |

Вход, выход и неудачный вход уже есть в `audit_log` (с IP и браузером), старт
часов — в `registrations.started_at`, запросы — в `query_log`, ответы — в
`submissions`. Дублировать их в `participant_events` не нужно: лента собирает
их при чтении (раздел 4).

### 2.2. Сигналы браузера: как они доходят

- Экран олимпиады копит сигналы в памяти и отправляет пачкой: раз в 10 с, а
  также сразу при скрытии страницы и при `pagehide` (`keepalive`, как
  автосохранение).
  - в пачке не больше 50 событий;
  - не больше 12 пачек в минуту на учётную запись, отказы тоже считаются
    (правило 13);
  - маршрут `POST /contests/{id}/play/signals`, пропуск через тот же `Access`,
    что и у остальных маршрутов `/play`.
- Сервер проверяет вид события, обрезает поля до пределов и ставит своё время
  (`created_at`). Время браузера сохраняется отдельно, только как заявленное.
- Уход считается, когда страница скрыта (`visibilitychange`) **или** окно
  потеряло фокус (`blur`). Уходы короче 1 с не записываются.
- Вставка ловится на редакторе SQL, поле ответа и заметках. Записываются
  место вставки, число символов и первые 500 символов текста.

### 2.3. Смена IP и параллельные сессии: на сервере, без записи на каждый запрос

- **Смена IP.** Для каждой регистрации в кэше хранится последний адрес, с
  которого пришёл её запрос к `/play` или к консоли. Если адрес другой,
  пишется одно событие `ip_changed` и значение в кэше обновляется. Пока адрес
  не меняется, в базу не пишется ничего (правило 6).
- **Параллельная сессия.** Так же хранится «последняя сессия этой регистрации»
  — хеш идентификатора сессии и время. Если запрос пришёл от другой сессии,
  пока прошлая была активна последние 2 минуты, пишется событие
  `parallel_session`. Повтор для той же пары сессий — не чаще раза в 10 минут.
- Адрес — `httpx.ClientIP`, не групповой ключ ограничителя (правило 9).
- **К каждому SQL-запросу добавляется адрес:** новая колонка `query_log.ip
  inet`, пишется в той же вставке, что и сам запрос. Так в отдельной вкладке
  запросов видно, откуда пришёл каждый.

### 2.4. История заметок и вкладок — таблица `workspace_revisions`

```sql
CREATE TABLE workspace_revisions (
    id              bigserial PRIMARY KEY,
    registration_id uuid NOT NULL REFERENCES registrations ON DELETE CASCADE,
    document        text NOT NULL,        -- 'notes' или id вкладки
    title           text,                 -- название вкладки в этот момент
    body            text NOT NULL,
    started_at      timestamptz NOT NULL, -- первая правка, попавшая в ревизию
    updated_at      timestamptz NOT NULL  -- последняя правка, попавшая в ревизию
);
CREATE INDEX workspace_revisions_document_idx ON workspace_revisions (registration_id, document, id);
```

Как пишется. Это оптимизация: автосохранение шлёт до 40 записей в минуту, и
хранить каждую — это до 64 КиБ на запись.

- В той же транзакции, что и сохранение заметок или вкладки:
  - если последняя ревизия документа моложе **30 с**, она обновляется на месте
    (`body`, `updated_at`);
  - иначе вставляется новая.
- Итого не больше двух ревизий в минуту на документ, а последнее состояние
  сохранено всегда.
- Тело, совпадающее с последней ревизией, ничего не пишет.
- Удалённая вкладка сохраняет свою историю: ревизии привязаны к регистрации, а
  не к вкладке.

## 3. Запросы, которые привели к ответу

К каждой попытке ответа экран показывает запросы участника, выполненные после
его предыдущей попытки на **любой** вопрос (или от старта часов, если это
первая) и до этой попытки. Считается при чтении: диапазон по
`query_log (registration_id, executed_at)` — индекс уже есть. Новые данные для
этого не нужны.

## 4. API для организатора

Все маршруты — под `/contests/{id}/monitor/…`. Проверки: `Authenticate`,
`Authorize(contest.monitor, contestID)`, отдельный бюджет частоты чтения на
учётную запись. Идентификатор регистрации проверяется на принадлежность этой
олимпиаде: чужая даёт 404, как несуществующая.

- **`GET /monitor/participants` — таблица участников со счётчиками.**
  - Поля строки:
    - запросы: всего, ошибки, отказы;
    - ответы: верные, неверные;
    - уходов: число и суммарное время;
    - вставок;
    - смен IP и параллельных сессий;
    - последняя активность;
    - статус регистрации;
    - флаги подозрительного (раздел 5).
  - Один агрегирующий SQL по индексам.
  - Для живого режима — кэш на 3 с на олимпиаду с single-flight, как у
    лидерборда: сорок организаторских вкладок, опрашивающих каждые 5 с, —
    один расчёт.
- **`GET /monitor/feed?after=<cursor>&kinds=…&participant=…` — общая лента.**
  - Слияние событий всех источников: `query_log`, `submissions`,
    `participant_events`, вход и выход из `audit_log` по участникам
    олимпиады.
  - Сортировка по времени, keyset-курсор.
  - Каждый источник читается своим индексированным диапазоном с `LIMIT`, и
    уже эти куски сливаются.
  - Не больше 200 записей на страницу.
- **`GET /monitor/participants/{registrationId}/timeline?…`** — та же лента по
  одному участнику, с фильтрами по виду события и по времени.
- **`GET /monitor/participants/{registrationId}/queries?status=…&q=…&cursor=…`** —
  отдельно SQL-запросы: полный текст, статус, ошибка, длительность, строки,
  время, IP. Поиск по тексту идёт через `escapeLike` (правило 3) и
  использует существующий GIN-индекс `query_log_sql_text_idx`.
- **`GET /monitor/participants/{registrationId}/answers`** — попытки ответа по
  вопросам, у каждой — запросы, которые к ней привели (раздел 3).
- **`GET /monitor/participants/{registrationId}/workspace`** — текущие заметки и
  вкладки и список ревизий. `GET …/workspace/revisions/{id}` отдаёт одну
  ревизию целиком.
- **`GET /monitor/participants/{registrationId}/export.csv`** и
  **`GET /monitor/export.csv`** — вся лента в файл, потоком. Предел по
  строкам и времени — как у CSV журнала участника.

Живой режим — опрос: экран организатора спрашивает `feed?after=<последний
курсор>` раз в 5 с, пока вкладка видна, а таблицу участников — раз в 5 с из
кэша. Отдельного SSE-канала нет: опрос по курсору — один индексированный
диапазон, и он не держит соединение на каждого организатора.

## 5. Отметки подозрительного

Считаются в том же агрегирующем запросе. Это подсказки, а не приговор:

- **Несколько IP** — больше одного адреса за олимпиаду.
- **Параллельные сессии** — хотя бы одно событие `parallel_session`.
- **Долгие уходы** — суммарно больше 5 минут вне страницы или больше 10
  уходов.
- **Ответ без запросов** — верный ответ, перед которым с прошлой попытки не
  было ни одного успешного запроса.
- **Крупная вставка** — вставка больше 200 символов в редактор или в поле
  ответа.
- **Одинаковые запросы** — точно такой же текст запроса (без учёта пробелов и
  регистра), как у другого участника этой олимпиады, со статусом `ok`, и не
  короче 60 символов.
  - Считается по хешу нормализованного текста.
  - Новая колонка `query_log.sql_fingerprint bigint` с индексом
    `(registration_id, sql_fingerprint)`, пишется при вставке.

Пороги — константы в коде с комментарием, не настройки.

## 6. Экран организатора

- Новая вкладка олимпиады **«Наблюдение»** (`/contests/[id]/monitor`).
  - Слева — таблица участников:
    - счётчики;
    - флаги-значки;
    - сортировка;
    - фильтры: только с отметками, по статусу, поиск по имени.

    Строки подсвечиваются, когда у участника появляется новое событие.
  - Справа — живая лента всей олимпиады. Фильтры по виду события;
    автопрокрутка отключается, когда организатор прокрутил ленту вверх.
- Страница участника (`/contests/[id]/monitor/[registrationId]`) с вкладками:
  - **Лента** — всё подряд, фильтры по виду и по времени;
  - **SQL-запросы** — отдельная вкладка: полный текст с подсветкой, статус,
    ошибка, IP, поиск и фильтр по статусу;
  - **Ответы** — попытки по вопросам, у каждой раскрываются запросы, которые
    к ней привели;
  - **Рабочее место** — заметки и вкладки сейчас и история ревизий: список
    по времени, при выборе видно тело ревизии и отличия от предыдущей;
  - **Входы и сети** — входы и выходы, адреса, браузеры, параллельные сессии.
- Кнопка «Скачать CSV» — на странице участника и на общей.

## 7. Аудит просмотров

- Просмотр ленты участника, его запросов и рабочего места пишет в
  `audit_log` действие `contest.monitor_view` (кто, чью регистрацию) — не
  чаще раза в 15 минут на пару «организатор — участник» (ключ в кэше). Иначе
  живой опрос раз в 5 с превратил бы аудит в шум.
- Выгрузка CSV пишется в аудит всегда: `contest.monitor_export`.

## 8. Что видит участник

- **Под заголовком экрана олимпиады** — одна строка: «Организатор видит ваши
  запросы, ответы, заметки и действия на этой странице». Тексты на
  en/ru/ro.
- **В заметках** под полем вместо фразы о личном пространстве — «Заметки видит
  организатор».

## 9. Производительность

- **Запись.** Новая нагрузка — пачка сигналов раз в 10 с на участника (одна
  вставка многих строк) и не больше двух ревизий в минуту на документ. Смена
  IP и сессии пишутся только при изменении.
- **Чтение.** Каждый маршрут — диапазон по индексу, никаких сканирований
  `query_log` целиком. Таблица участников — один запрос, кэш на 3 с,
  single-flight. Лента — keyset по курсору, не больше 200 строк.
- **Индексы** добавляются в той же миграции, что и таблицы (правило 7):
  - `participant_events (registration_id, id)`;
  - `participant_events (contest_id, id)`;
  - `workspace_revisions (registration_id, document, id)`;
  - `query_log (registration_id, sql_fingerprint)`.
- **Проверка.** Нагрузочная проверка на `cmd/consoleload` с 40 участниками:
  время запроса консоли не должно заметно вырасти.

## 10. Миграция и выпуск

- Миграция `000033_participant_monitoring`:
  - таблицы `participant_events` и `workspace_revisions`;
  - колонки `query_log.ip` и `query_log.sql_fingerprint`;
  - индексы;
  - право `contest.monitor` для ролей, у которых есть `contest.view`.
- Старые записи `query_log` остаются без IP и отпечатка.
- В примечаниях к выпуску:
  - заметки и вкладки больше не личные;
  - участники должны видеть уведомление на экране (раздел 8).
