# Удаление аккаунтов и массовые операции над ними

Дата: 2026-09-03. Статус: согласовано, готово к плану реализации.

## Задача

Администратору нужны две вещи, которых сейчас нет: удаление аккаунта и
применение одного действия сразу к нескольким выбранным аккаунтам. Сегодня
есть только поштучные создание, блокировка, разблокировка, смена ролей, сброс
пароля и массовый импорт новых аккаунтов.

## Принятые решения

Зафиксированы в обсуждении, дальше не пересматриваются.

1. **Удаление мягкое.** Строка остаётся, результаты олимпиад и след аудита
   целы.
2. **Причина обязательна** и для удаления, и для блокировки.
3. **Массовыми становятся все перечисленные действия:** блокировка,
   разблокировка, удаление, смена ролей, сброс паролей.
4. **Логин удалённого аккаунта освобождается** сразу.

## Почему удаление — это статус, а не отдельная колонка

Вход (`internal/auth/service.go:155`) и каждый запрос к API
(`internal/auth/middleware.go:126`) уже упираются в `user.IsActive()`, то есть
в `status == 'active'`. Третий статус закрывает обе двери, не добавляя ни
одной новой проверки, которую можно забыть поставить. То же касается
`CountActiveWithRole` (`internal/postgres/users.go:216`): он считает по
`u.status = 'active'`, поэтому удалённый администратор перестаёт считаться
администратором сам собой.

Отдельная колонка `deleted_at` потребовала бы править каждое из этих мест
руками — и одно забытое место означает, что удалённый аккаунт продолжает
работать.

## Данные (миграция 000015)

1. `CHECK` статуса расширяется до `('active', 'blocked', 'deleted')`.
2. Три колонки объясняют **текущий** статус, одна пара на блокировку и на
   удаление, потому что объясняется именно статус:
   `status_reason text`, `status_changed_at timestamptz`,
   `status_changed_by uuid REFERENCES users`.
3. `users_login_lower_key` пересоздаётся частичным:
   `CREATE UNIQUE INDEX ... ON users (lower(login)) WHERE status <> 'deleted'`.
   Уникальность `email` — так же. Логин освобождается в момент удаления.
4. `CREATE INDEX users_status_idx ON users (status)` — список теперь
   фильтруется по статусу на каждом запросе (см. ниже), а правило 7 из
   `CLAUDE.md` требует, чтобы индекс приходил вместе с фильтром.

Блокировка на время пересоздания индексов не рассматривается как проблема:
таблица размера университета, а не биллинга.

## Скрытый баг, который надо закрыть этой же миграцией

`Users.List` фильтрует статус как `($2 = '' OR u.status = $2)` — пустое
значение означает «все». Как только появится `'deleted'`, список по умолчанию
начнёт показывать удалённых. Условие становится
`CASE WHEN $2 = '' THEN u.status <> 'deleted' ELSE u.status = $2 END`:
удалённые видны, только когда их запросили явно.

## Домен (`internal/users`)

**Константа** `StatusDeleted = "deleted"`.

**`Delete(ctx, actorID, userID, reason)`** отказывает на себе
(`ErrCannotActOnSelf`) и на последнем администраторе
(`ErrLastAdministrator`), ставит статус, поднимает `SessionGeneration` и пишет
аудит. Поднятие поколения обязательно по той же причине, что у блокировки:
без него аккаунт продолжает работать во всех уже открытых вкладках.

**`Restore(ctx, actorID, userID)`** возвращает статус `active`. Отказывает
существующими `ErrLoginTaken` и `ErrEmailTaken`, если за это время логин или
почту занял живой аккаунт — это прямая цена решения освобождать логин. Оба
сентинела уже объявлены и уже отображены в `fail`, новых заводить не нужно;
сообщение должно называть занятое значение.

**`Block`** получает параметр причины. Причина обязательна
(`ErrReasonRequired`) и ограничена по длине — правило 2 из `CLAUDE.md`:
колонка `text` не является границей.

**Массовые операции — новый файл `bulk.go`.** Три метода:
`BulkSetStatus`, `BulkReplaceRoles`, `BulkResetPassword`. У каждого свой
естественный вход и выход, общий у них только внутренний разбор выбора.
Результат по образцу `ImportResult`:
`Changed []uuid.UUID` и `Skipped []SkippedAccount{ID, Login, Reason}`.
Потолок — 500 идентификаторов на запрос (`ErrTooManyAccounts`).

`Reason` берётся из того же словаря строковых констант, что и импорт
(`SkipLoginTaken`, `SkipInvalidRow` рядом с ними): добавляются
`SkipNotFound`, `SkipSelf`, `SkipLastAdministrator`, `SkipAlreadyInStatus`.
Словарь конечный и локализуется на фронтенде так же, как причины импорта.

Новые действия аудита: `user.delete`, `user.restore`. У `audit.Recorder`
сейчас только `Record(ctx, Entry)`; для массовых операций добавляется
`RecordMany(ctx, []Entry)` — иначе одна запись на аккаунт сводит на нет весь
смысл пакетного применения.

## Устройство массовой операции: сначала разбор, потом применение

Это главное архитектурное решение, и оно же ответ на требование
оптимальности.

**Наивный цикл по одиночным методам порочен дважды.** На 500 аккаунтах это
около двух тысяч запросов: `ByID` на каждого, `COUNT` администраторов на
каждого, своя транзакция и своя запись аудита. И он **неверен**:
`refuseIfLastAdmin` внутри цикла считает заново на каждой итерации, не видя
решений предыдущих, поэтому блокировка двух последних администраторов одним
выбором пройдёт целиком.

**Правильная форма — две фазы.**

*Фаза разбора* не делает ни одной записи. Один `ByIDs` вытаскивает весь выбор
(`WHERE id = ANY($1)`), бюджет администраторов считается **один раз** и
уменьшается по ходу перебора. Каждый аккаунт попадает либо в список к
применению, либо в `Skipped` с причиной: не найден, это вы сами, последний
администратор, уже в этом статусе. Фаза чистая и тестируется без базы.

*Фаза применения* берёт выживших и выполняется **одной транзакцией**
множественными записями:

- `SetStatusMany` — один `UPDATE ... WHERE id = ANY($1)` вместе с причиной,
  автором и временем;
- `BumpSessionGenerationMany` — один `UPDATE` на весь набор;
- `ReplaceRolesMany` — один `DELETE ... WHERE user_id = ANY($1)` и один
  `INSERT ... SELECT` из `unnest` в перекрёстном соединении с ролями;
- аудит — один многострочный `INSERT ... SELECT * FROM unnest(...)` вместо
  записи на аккаунт.

Так получаются оба нужных свойства сразу: частичный успех со внятным списком
пропущенных — и порядок десятка запросов вместо двух тысяч.

**Исключение — сброс паролей.** Здесь дорога не база, а argon2id: он
намеренно медленный, около 50–100 мс на хеш, и 500 паролей подряд — это
десятки секунд процессорного времени. Хеши считаются параллельно пулом
ограниченного размера (как `provisioning.DefaultWorkers`), а затем
записываются одним `UPDATE ... FROM unnest($1::uuid[], $2::text[])`.

## HTTP (`internal/api`)

Поштучно: `POST /users/{userID}/delete` с телом `{reason}` и
`POST /users/{userID}/restore`. У `POST /users/{userID}/block` в теле
появляется `reason`.

Массово: `POST /users/bulk/status`, `POST /users/bulk/roles`,
`POST /users/bulk/password-reset`. Каждая отвечает 200 с разбором по
аккаунтам и **никогда** не превращает один негодный идентификатор в 500 —
негодный идентификатор это `Skipped`, а не отказ операции.

Два новых сентинела — `ErrReasonRequired` и `ErrTooManyAccounts` — получают
отображение в `fail` и тест обработчика на
конкретный 4xx — правило 1 из `CLAUDE.md`. Все ручки под правом
`users.manage`.

## Фронтенд

Страница `/users` остаётся серверным компонентом. Клиентскими становятся
только панель выбора и диалоги — ровно то, что требует состояния.

- Флажок в строке аккаунта, панель выбора («выбрано 12») с действиями:
  заблокировать, разблокировать, удалить, роли, сбросить пароли.
- Диалог требует причину там, где она нужна, и не даёт отправить пустую.
- Фильтр статуса получает «удалённые»; по умолчанию они скрыты.
- В карточке аккаунта — удаление с причиной, восстановление для удалённого и
  показ причины, автора и даты смены статуса.
- Итог массовой операции — панель «изменено / пропущено с причиной», как на
  экране импорта.

**Ограничение по бюджету бандла.** Новые клиентские компоненты берут
константы и хелперы из `lib/api/accounts-terms.ts`, а **не** из модулей со
схемами: модуль, вызывающий `z.object()` на верхнем уровне, затягивает zod в
клиентский бандл. Это только что стоило 280 КБ на семи маршрутах и было
вычищено; новый код не должен вернуть их обратно.

Действия идут через Server Action и `revalidatePath`, а не через клиентский
`fetch`.

## Проверки

Доменные (`bulk_test.go`, `service_test.go`):

- последнего администратора нельзя удалить ни поштучно, ни в составе выбора —
  и выбор из двух последних администраторов пропускает второго, а не обоих;
- себя нельзя удалить;
- у удалённого поднято поколение сессии;
- причина обязательна и ограничена по длине;
- потолок в 500 идентификаторов соблюдается;
- разбор выбора не открывает транзакцию (счётчик `Calls` у тестового
  `UnitOfWork` — он для этого и заведён);
- применение укладывается ровно в одну транзакцию.

Обработчики (`users_handler_test.go`): каждый новый сентинел даёт свой 4xx;
негодный идентификатор в массовой ручке даёт 200 и `Skipped`.

Репозиторий на живом Postgres (`internal/postgres`): логин освобождается
после удаления и переиспользуется; восстановление при занятом логине падает
на частичном индексе; список по умолчанию не показывает удалённых;
удалённый администратор не считается в `CountActiveWithRole`.

Сквозные (`internal/auth`): удалённый не входит и не проходит middleware.

Фронтенд: панель выбора, обязательность причины, отображение пропущенных.

## Что намеренно не делается

- **Жёсткое удаление и обезличивание.** Мягкого удаления достаточно для
  поставленной задачи; обезличивание — отдельное необратимое действие с
  собственными требованиями.
- **Массовое редактирование профиля** (имя, почта). Осмысленного массового
  значения у этих полей нет.
- **Отмена массовой операции одной кнопкой.** След аудита позволяет
  разобраться, а обратное действие делается тем же массовым выбором.
