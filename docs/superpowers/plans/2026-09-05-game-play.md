# Шаг 5 «Игра» — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.

**Goal:** участник видит историю и вопросы, отвечает на них, ответы проверяются автоматически и считаются по правилам олимпиады, время идёт по серверу.

**Architecture:** решения приняты в `docs/ARCHITECTURE.md` разделы 6.1, 6.1.1, 8, 5. План их реализует и не переоткрывает.

**Tech Stack:** Go 1.23, pgx/v5, chi, PostgreSQL 16; Next.js 16 App Router, React 19.

## Global Constraints

Держат каждую задачу без исключений.

- **Правило студента.** Участник — недоверенная сторона. Каждая проверка, которая решает, что ему можно, живёт на сервере. Правило, которое живёт только в интерфейсе, не является правилом (раздел 6.1.1 дословно). Спрятать в UI недостаточно нигде.
- **Эталонные ответы не покидают сервер участнику.** Ни в одном ответе API, ни в одном событии SSE, ни в тексте ошибки.
- `CLAUDE.md` правило 1: каждая ошибка, доходящая до HTTP, — объявленный сентинел с отображением в `fail` и тестом обработчика на конкретный 4xx.
- `CLAUDE.md` правило 2: у каждого поля и списка, доходящего до хранилища, явная граница в домене.
- `CLAUDE.md` правило 7: фильтр, который предлагает API, приходит с индексом в том же изменении.
- `CLAUDE.md` правило 10: гарантия доказывается на том пути, которым пользуется деплой.
- Go: `foo.go` тестируется `foo_test.go`; домен не импортирует драйвер БД; HTTP принадлежит слою HTTP; у каждого пакета доккомментарий. Комментарии по-английски, проза документации по-русски. testify в Go не используется.
- Фронтенд: клиентские компоненты берут константы из `lib/api/*-terms.ts`, никогда из модулей со схемами; страницы остаются серверными; каждая видимая строка в трёх локалях.
- Разделители `---` в прозе не используются.
- **UI участника прост, но полон.** Олимпиада идёт на время: экран не должен требовать изучения. Никаких настроек, вкладок и панелей, без которых можно обойтись — но всё, что нужно (история, вопросы, поле ответа, оставшиеся попытки, часы), доступно без поиска.

## Порядок и почему он такой

Дедлайн первым: на него опирается всё остальное, и он же — то, чем участник ломает олимпиаду, если формула разойдётся между путями. Затем чтение (история и вопросы), затем запись (ответы), затем правила подсчёта, затем часы, затем экраны.

## Task 1: единая формула дедлайна участника

**Files:** `backend/internal/contests/deadline.go` + тест; вызовы в `internal/queryproxy`.

Раздел 8: `fixed` — `deadline = ends_at`; `individual` — `deadline = LEAST(started_at + duration_min, ends_at)`. **Другой логики тайминга в коде не существует** — путь ответа, queryproxy и SSE считают дедлайн одной и той же функцией.

Сейчас queryproxy проверяет «олимпиада идёт» своей проверкой. Свести к одной функции. Грейс на сетевые задержки конфигурируется, по умолчанию 5 секунд, и применяется только к приёму, не к показу.

Тесты: обе модели; `individual`, где `started_at + duration` выходит за `ends_at` (побеждает `ends_at`); участник, не начавший при `individual`; олимпиада без `ends_at`, если такое состояние возможно.

**Проверка в конце:** может ли участник продлить себе время — подменой чего угодно, что приходит от клиента.

## Task 2: история и вопросы для участника

**Files:** `backend/internal/api/participant_handler.go` + тест; чтение в `internal/contests`.

`GET /contests/{id}/story` и `GET /contests/{id}/questions` для записанного участника идущей олимпиады.

Отдаётся: история на языке участника, видимые вопросы (`is_visible = true`) с формулировкой, номиналом, числом оставшихся попыток и признаком «закрыт». **Не отдаётся** ни при каких условиях: эталонные ответы, `penalty_pct` соседних вопросов, скрытые вопросы, что-либо о других участниках.

Скрытый вопрос существует полноценно и просто не показывается (раздел 6.1) — он обязан остаться отвечаемым, если олимпиада так задумана, поэтому «не показывать» и «не принимать ответ» — разные решения; здесь только первое.

Доступ: записан, олимпиада `running`, адрес разрешён — те же условия, что уже проверяет queryproxy. Переиспользовать их, а не написать вторые.

**Проверка в конце:** может ли участник прочитать чужую олимпиаду, черновик, скрытый вопрос или эталон — прямым запросом, подменой идентификатора, сменой языка.

## Task 3: отправка ответа с автопроверкой

**Files:** `backend/internal/contests/submission.go` + тест; обработчик и маршрут; миграция, если нужен индекс.

`POST /contests/{id}/questions/{questionId}/answer` с телом `{value}`.

В одной транзакции: проверить дедлайн по часам core-БД (раздел 8: просроченный ответ не принимается даже при мёртвом шедулере), взять номер попытки, сверить с эталоном по правилу вопроса (`match_kind`), записать `submissions`, обновить `registrations.total_score`.

Границы: длина ответа ограничена в домене; число попыток — `max_attempts`; повторный ответ на закрытый вопрос отвергается сентинелом.

Гонка: два одновременных ответа не должны дать один `attempt_no` дважды или превысить `max_attempts`. `UNIQUE (registration_id, question_id, attempt_no)` есть в схеме — опереться на него, а не на чтение-затем-запись.

**Проверка в конце:** может ли участник ответить после дедлайна, превысить попытки, ответить за другого, получить баллы дважды, узнать эталон по разнице ответов сервера.

## Task 4: штраф и последовательное прохождение

**Files:** `internal/contests/submission.go`, `publish.go` + тесты; миграция для `questions.penalty_pct` и `contests.progression`, если их ещё нет.

Раздел 6.1.1, дословно:

- Штраф применяется в момент ответа, результат пишется в `submissions.points_awarded` и **никогда не пересчитывается** из текущей настройки.
- Пол — ноль за вопрос, в минус уйти нельзя.
- Штраф и `max_attempts` — две ручки одного механизма, обе можно ставить сразу; если штраф обнулил вопрос раньше, оставшиеся попытки бесплатны.
- В режиме `winner` штраф **не применяется**, но и не запрещается настройкой.
- `sequential`: следующий вопрос открывается, когда предыдущий закрыт — отвечен верно **или** попытки исчерпаны. Скрытые вопросы считаются в последовательности наравне.
- Гейт публикации **отказывает** при `sequential` + вопрос без `max_attempts`.
- Имеет смысл только при `question_mode = multi`.

**Проверка в конце:** может ли участник ответить на ещё не открытый вопрос прямым запросом; может ли организатор, поменяв процент посреди олимпиады, переписать уже набранные баллы.

## Task 5: таймер и SSE

**Files:** `backend/internal/api/events_handler.go` + тест; фоновый переход статусов.

`GET /contests/{id}/events` — SSE. При загрузке фронтенд получает `server_now` и **свой** `deadline`; ресинхронизация раз в 30–60 секунд; события `contest_started` / `contest_finished`.

Раздел 8: смена статусов — фоновым шедулером с advisory lock, не удерживаемым между тиками. **Гарантия закрытия от шедулера не зависит** — она в транзакции ответа (Task 3).

Границы: сколько соединений держит один участник, что происходит при обрыве, чем ограничен поток.

**Проверка в конце:** может ли участник держать тысячу соединений; узнаёт ли он через SSE что-либо о других; переживает ли канал перезапуск.

## Task 6: экраны участника

**Files:** `frontend/app/(participant)/contests/[contestId]/play/*`.

История, список вопросов, поле ответа, оставшиеся попытки, часы. Консоль SQL уже есть — вопросы и история встают рядом с ней, а не отдельным путешествием: во время олимпиады переключение между экранами стоит времени.

Простое, но полное: участник за один взгляд видит, сколько осталось времени, какие вопросы открыты, сколько попыток осталось, и может ответить не уходя с экрана.

**Проверка в конце:** видит ли интерфейс что-либо, чего не должен; ведёт ли себя честно при истёкшем времени; не ломается ли при нулевом числе вопросов.
